# Freedom CQA: план сдачи — последний час

## ДО открытия контрольных данных

1. Рабочие оценки DEV: лучше **65/65 status=ok**; обязательно все 65 ID в results/dev/results.json. Голосовые DEV-звонки могут быть неточны для `contact`, но для `status=ok` значение **только true/false**, с обоснованием (не null). Не выдавайте выдуманные реплики за факт.
2. Убедитесь, что GROQ/QWEN API запущен и у него достаточно квоты на **10 контрольных чатов + запасные попытки**. Сохранённые результаты сохраняются в `cqa.sqlite3`.
3. Сделайте `git push` работающего кода, README и **DEV JSON** до открытия контроля, чтобы последний час тратить на 10 чатов.
4. Проверьте команду и `model.name` в DEV JSON. Не публикуйте ключи, raw client data, `.env`, SQLite.
5. Откройте новую вкладку «Сдача JSON» и проверьте, что она запускается. Прогоните 36 автоматических тестов.

## В последний час после выдачи контрольного набора

1. Получите официальный контрольный набор и его `dataset_group_id` / URL **способом, который сообщат организаторы**. Приложение к гайду **не обещает новый LLM API key**.
2. В «Диалоги» импортируйте контрольный JSON или официальную GET-ссылку. Проверьте **ровно 10 уникальных conversation_id**. Не загружайте их в `DEV`.
3. Если организаторы изменили формулировку одного критерия — «Чек-лист» → измените **правило существующего ID 01–08** и сохраните новую версию. Для схемы 1.0 **нельзя добавлять девятый ID или менять типы и допустимые шкалы**.
4. Выберите **новый dataset_group_id** в фильтре диалогов. Нажмите «Оценить новые». Дождитесь завершения. Проверяйте ошибки `429/503` и недостающие оценки.
5. «Сдача JSON» → настоящее название команды → контрольный набор → актуальная версия чек-листа → **Сформировать PROD JSON (10)**. Проверьте: `total: 10`, `error: 0` (по возможности), правильный `model.name` и `evidence_turns`.
6. Если несколько ошибок: попытайтесь повторно оценить **только неоценённые** диалоги через batch; не перезаписывайте проверенные результаты без нужды. `status:error` допустим по схеме, но оценка потеряна для этого диалога.
7. Проверьте файлы программно:

   ```powershell
   .\.venv\Scripts\python.exe scripts\validate_results.py --kind dev --group DEV --checklist-id checklist-v1
   .\.venv\Scripts\python.exe scripts\validate_results.py --kind prod --group ACTUAL_CONTROL_GROUP --checklist-id ACTUAL_CHECKLIST_ID
   ```

8. Выполните **`git add .`**, **`git commit`**, **`git push`** до стоп-кода. Убедитесь на GitHub, что **оба** файла опубликованы в корне репозитория.

## Нельзя

- Публиковать `.env`, ключи к Gemini/Groq или signed GET URL.
- Использовать `null` для `contact`, `empathy`, `dialogue`, `critical`.
- Нумеровать только реплики оператора: счёт с 1 по ВСЕМ репликам.
- Смешивать DEV и контрольные ID.
- Заменять неудачную оценку `0/100`: нужен `status:"error"`, `criteria:[]`, `score:null`.
- Считать локальный файл или локальный commit окончательной сдачей без **push**.
